# M1.4 — RadialKnowledgeGraph Responsive Review Findings

**Status:** Inspection complete. **No code changes made.**
**Scope:** Route `/predictive-os`, component `RadialKnowledgeGraph` (`src/lib/v5Interactions.tsx:844–1015`) and its host section in `PredictiveLifeOS.tsx:1631–1893`.
**Viewports audited:** 375, 430, 768, 1024, 1280, 1440 px.
**Prior state:** M1.3 (commit `45fc8f8`, tag `v5.5.1-alpha.m1.3`).
**Methodology:** Seven diagnostic Playwright specs (`tests/e2e/_kg-*.spec.ts`, to be deleted before any commit). Each measures live DOM at the target viewport: element boundingClientRect, scrollWidth, computed style, ancestor chain, grid track resolution, label bbox collisions, node-off-viewport counts.

---

## 1. Executive summary — one sentence

> **M1.3 fixed the SVG's *own* geometry (aspect ratio, max size) but did not fix the layout system around it. Two independent intrinsic-min-content offenders (one on mobile, one on desktop) are inflating the KG section's grid tracks far beyond the viewport, and `body { overflow-x: hidden }` is silently clipping the resulting disaster.** The failure has nothing to do with fixed node coordinates, ring radii, or SVG viewBox math — the KG SVG itself is perfectly well-behaved. The failure is that (a) the SVG size is hardcoded to 520 with no viewport awareness, and (b) two adjacent surfaces (metadata table, encyclopedia article) burst the containing grid track, moving the KG panel off-screen at every viewport ≤ 1440.

The user's framing is therefore correct: this is not a CSS hardening bug. The KG's *information architecture* and *interaction density* are the same at 375 px and 1440 px, and neither of those densities is right at either end. A different graph mode is required per breakpoint.

## 3. Root causes — mapped to the user's six categories

### 3.1 Fixed node coordinates — ❌ NOT A CAUSE

Positions are computed as `x = cx + r · cos(rad)`, `y = cy + r · sin(rad)` where `cx = cy = size/2` (`v5Interactions.tsx:873–887`). They scale with `size`. The viewBox is `0 0 size size` and `preserveAspectRatio="xMidYMid meet"` (line 907–908). If `size` were driven by container width, coordinates would follow — the geometry is correct. **Not the defect.**

### 3.2 Fixed radii — ⚠️ CORRECT BUT DECEPTIVE

Ring radii are `[size*0.16, size*0.30, size*0.44]` (`v5Interactions.tsx:875`) — proportional to `size`. Node radius is fixed at `16` (30 for center) in viewBox units (line 887, 891); label offset `p.y + p.r + 14` (line 995); font size 10/11 (line 998); hit radius `Math.max(p.r + 8, 22)` (line 955). All of these scale with the rendered SVG because they live in viewBox space — they *look* right in the SVG when SVG is 520 px, and they *look* right at 260 px too, just at half the pixel density. **In principle scaling works.** In practice `size` is a constant.

**However:** the *ratio* of node size to ring diameter is such that at 260 px rendered width, node radius shrinks to 8 CSS px (16 × 260/520), which puts the *visible* node under the 44 × 44 minimum tap target. The invisible hit-circle `hitR = Math.max(p.r + 8, 22)` remains 22 viewBox units = 11 CSS px at 260 rendered → 22 CSS px diameter, well under 44 CSS px. **Below ≈ 640 px SVG width, hit targets fall below WCAG 2.5.5.** Not a *layout* defect, but a hard usability one that any responsive scheme must fix.

### 3.3 Label positioning — ⚠️ CONTRIBUTING FAILURE (secondary)

- Labels sit at `y = p.y + p.r + 14` (line 995), textAnchor="middle". At ring 2 (`r = size · 0.30`) around the equator, ring-1 and ring-2 labels on the same angular slice can vertically bump. This is a *depth density* problem, not a positioning-math problem.
- Labels are truncated `label.slice(0, 18) + '…'` when `> 20` chars (line 1004). Truncation is uniform regardless of viewport — at 260 px SVG, labels of 18 characters wrap into the neighboring ring and overlap the outer ring's nodes. At 520 px they fit.
- The SVG has `overflow: visible` (line 909). Combined with the fact that `<text>` elements' bounding rects contribute to the SVG element's own layout width in some browsers, this is why the KG section's `textContent` measurement showed concatenated node labels ("My PortfolioProperty OpsCapital Stack…") in earlier chain traces. **The `overflow: visible` decision is a deliberate M1.3 choice** so external labels aren't clipped, but it means the SVG element's border box no longer represents drawn area — the parent has to lay out around the concatenated text.

**Verdict:** the label *math* is fine, but the *label strategy* (always draw all 12–13 labels, truncated to 18 chars) is incompatible with narrow containers.

### 3.4 Parent constraints — ✅ **PRIMARY MOBILE FAILURE**

The KG panel's `S.section` container has **no `min-width: 0`** override on its grid item participation. In the outer `1fr 1fr` grid at ≥ 1025 px (line 1640), the section's grid track resolves to `max(1fr, min-content of children)`. Its children include the M1.3 metadata table.

**The M1.3 metadata `<table>`:**
- Style declaration: `S.kgMetaTable(isXS)` (line 1329–1338) → `width: 100%; minWidth: isXS ? undefined : 720; display: isXS ? 'block' : 'table'; borderCollapse: 'separate'`.
- Structure: 13 rows × 9 columns. Each `<td>` has `whiteSpace: 'nowrap'` at ≥ 640 px (line 1377) — this is by design to keep values on one line for horizontal scroll.
- At XS the intent was `display: block` on `<table>` and `whiteSpace: normal` on `<td>` so the table becomes a stacked card list. But `display: block` on `<table>` **does not disable the internal table layout algorithm** — it makes the outer box a block-flow participant, while the browser still lays out the TD grid internally at each row's `min-content` width. Empirically: at 375 px, the table measures **1451 × 1451 px** (13 rows × 9 cells, each cell 260 px wide holding the text label + value). The `whiteSpace: normal` override applies but 260 px per cell is still forced by the un-wrappable words inside them (data values, category labels).
- The table's parent (`<div style="margin-top: 14px">`, line 1685) has no `overflow-x: hidden` or `min-width: 0` at XS. Its grandparent `S.section` has no `min-width: 0` either.
- Consequence: `S.section`'s intrinsic min-content = **max(SVG max-width 520, table min-content 1451) = 1451**. In the outer grid, this forces the track to 1507 (with padding). The single-column grid at `< 1025 px` (`gridTemplateColumns: '1fr'`) resolves the track against min-content of the wider child → **1507 px grid track at 375 px viewport**. The KG SVG then centers inside that track (`justifyContent: center`, line 1651) → SVG `left = (1507 – 520) / 2 = ~493` from the section's own left, and the section itself starts at `left = 92` (main padding + shell offset) → SVG absolute `left ≈ 566`. Off-screen by 191 px on a 375-viewport, hidden only by the body clip.

**This is the primary mobile defect.** The 520 SVG isn't overflowing on its own; it's being *pushed off-screen* by a sibling that demands 1451 px of intrinsic width.

### 3.5 SVG viewBox logic — ❌ NOT A CAUSE

`viewBox="0 0 ${size} ${size}"` with `preserveAspectRatio="xMidYMid meet"` (line 907–908) is textbook-correct. The SVG element style (line 909) `width: 100%; maxWidth: size; maxHeight: size; aspectRatio: 1/1; height: auto` is also correct — this is exactly the M1.3 responsive-SVG idiom. The `size` prop being hardcoded to `520` (`PredictiveLifeOS.tsx:1656`) means the SVG scales up to 520 and no further, but scales *down* fluidly if its wrapping div were < 520 wide. **The viewBox/preserveAspectRatio/aspect-ratio triple is not the defect. `size` being a constant is a design decision, not a math error.**

### 3.6 Graph topology density — ✅ **STRUCTURAL FAILURE**

Node counts per persona (source scan of `EncyclopediaEntry.ring` arrays):
- LANDLORD: 1 center + 4 (R1) + 5 (R2) + 3 (R3) = **13 nodes**, ~12 edges
- TENANT: 1 + 4 + 5 + 3 = **13**
- AGENT: 1 + 4 + 5 + 3 = **13**
- INVESTOR: 1 + 5 + 5 + 3 = **14**
- VENDOR: 1 + 2 + 0 + 0 = **3** (outlier — treats KG differently)
- Personas 5–8: similar to 1–4 (uses `streamlinedPersona()` builder line 837 onward)

At `size = 520`:
- Ring 3 diameter = 520 × 0.44 × 2 = **457 px** (label ring)
- Ring 2 diameter = 520 × 0.30 × 2 = **312 px**
- Ring 1 diameter = 520 × 0.16 × 2 = **166 px**
- Ring 3 has 3 nodes evenly spaced ⇒ arc between adjacent nodes ≈ 480 px. Comfortable.
- Ring 2 has 5 nodes ⇒ arc ≈ 196 px. Nodes are 32 px diameter → label truncated to 18 chars at font-size 10 ⇒ ~110 px label width. Adjacent labels touch when the angular position happens to put two labels above/below the same horizontal line (visible around the 3-o'clock and 9-o'clock positions).
- Ring 1 has 4–5 nodes ⇒ arc ≈ 104–130 px. Center node halo (r=34) extends 68 px from center; ring-1 nodes (r=16, at radius 83) leave ~15 px between center halo and inner edge of ring-1 node.

**At scaled-down widths (say 260 px SVG on tablet), all these arcs halve while node radius stays viewBox-constant → node halos start touching in ring 1.** This is inevitable with 13 nodes on 3 rings within a 520-viewBox square. **Fewer nodes / fewer rings / a different topology are the only real fix at narrow widths.**

### 3.7 Bonus (unlisted): outer-grid intrinsic min-content — ✅ **PRIMARY DESKTOP FAILURE**

The KG+Article split at ≥ 1025 px is:
```
grid-template-columns: 1fr 1fr; gap: 16; align-items: stretch
```
(PredictiveLifeOS.tsx:1637–1643)

`1fr` in CSS Grid means `minmax(auto, 1fr)`, where `auto` is min-content. The encyclopedia article panel (right column, `S.article` at line 1177) has no `min-width: 0` or `overflow: hidden` on itself. Its children include:
- A "Solution modules" list (line ~1870) — each solutionCard is a grid `40px 1fr auto` (`S.solutionCard`, line 1200) whose middle track resolves to **1371 px** when it holds an un-wrappable description.
- A "Related" pill row.
- Article body/definition paragraphs with `min-width: 0` on the flex container (line 1820) but not on the section.

**Measured at 1280 px:** article column resolves to **1519 px**, KG column shrinks to **464 px** (KG SVG then renders at 464 × 464), grid `gridTemplateColumns` computed to `"760.078px 1519.42px"` (or similar) → total 2287 + 16 gap + main padding = 2491. Body scrollW = 2723. **The right column overflows by ~1440 px at 1280 viewport and by ~1280 px at 1440 viewport.** Same class of defect as the mobile case — an intrinsic-content child inflates the grid track — different location.

**Verdict:** parent-constraint failure occurs at *both* ends of the breakpoint spectrum, in two separate grids, caused by two separate content offenders.

## 6. Why M1.3's Playwright suite passed

`tests/e2e/predictive-os-responsive.spec.ts` (15/15 pass) asserted per-viewport:
- SVG has some rendered width; ✓ (SVG is 520 at every viewport)
- Metadata table exists; ✓
- Card-stack `<tr>` display at XS; ✓ (`display: block` is applied, even though internal table layout still forces 1451 min-content)
- Sparkline clip; ✓

It did **not** assert:
- `body.scrollWidth <= viewport.width` — would have caught this immediately.
- SVG element `left` within `[0, viewport.width]` — would have caught the off-screen positioning.
- Node visible circles ≥ 44 CSS px (a11y) — would have caught D7/D8 at every non-desktop viewport.
- Node-to-node label collision count — would have caught D6 at narrow renders.
- Grid-track resolved widths — would have caught D2/D3 directly.

The M1.3 tests were **geometry compliance tests, not usability tests**, exactly as the user diagnosed. Any M1.4 suite must invert this: measure what the *user* would experience (scrollable overhang, off-screen content, tap-target adequacy, label legibility, collision) rather than what the SVG *element* looks like in isolation.

## 7. Proposed direction (design, not code)

This section is intentionally at design level. No implementation until approved.

### 7.1 Graph modes

```
GraphMode = 'mobile' | 'compact' | 'desktop' | 'wide'
```

| Mode | Viewport | maxDepth | maxVisibleNodes | labelMode | interaction | layout | Where SVG lives |
|------|----------|---------:|----------------:|-----------|-------------|--------|-----------------|
| mobile   | < 640    | 1 | selected + 1st-degree neighbors (≤ 6 rendered) | full label on focus, short label on peers | progressive disclosure: tap node → recenter + reveal neighbors; back button pops | vertical stack; graph replaced by a **focus explorer** (not a shrunk radial) — center pill + neighbor list + one animated ring | inside a container-relative wrapper |
| compact  | 640–1024 | 2 | 1 + ring 1 (4–5) + selected-branch of ring 2 (≤ 3) | short label, full on focus | tap-to-focus re-centers; radial preserved | constrained radial 320–420 CSS-px square, centered | KG column only; article column becomes an inline "Details" drawer under the graph |
| desktop  | 1025–1439 | 3 (full) | all (13) | full 18-char truncated labels | hover-highlight + click-to-open article | full radial 520 CSS-px in KG column; article panel to the right | `minmax(0,1fr) minmax(0,1fr)` split, both children `min-width: 0` |
| wide     | ≥ 1440 | 3 | all (13) with room to enlarge to 640 CSS-px | full labels, no truncation | hover + focus + preview tooltip | container-relative graph size (up to `min(640, availableWidth × 0.42)`); metadata table becomes a persistent right rail | 3-column: graph / article / metadata OR 2-column: graph / article-with-metadata-tabs |

### 7.2 `useGraphLayout()` shape

```ts
type GraphMode = 'mobile' | 'compact' | 'desktop' | 'wide'

interface GraphLayoutConfig {
  mode: GraphMode
  size: number                    // CSS-px, container-derived (not hardcoded)
  maxDepth: 1 | 2 | 3
  maxVisibleNodes: number         // clamp for selected-node subgraph
  labelMode: 'off' | 'short' | 'full' | 'on-focus'
  nodeRadiusCssPx: number         // ensures ≥ 22 CSS-px visible node in dense modes
  hitRadiusCssPx: number          // ≥ 22 CSS-px (44 diameter tap target)
  interaction: 'progressive' | 'tap-focus' | 'hover-open' | 'hover-preview'
  layout: 'explorer' | 'radial-constrained' | 'radial-full' | 'radial-wide'
}

function useGraphLayout(containerRef: RefObject<HTMLElement>): GraphLayoutConfig
```

The hook consumes both `useMobileBP()` (the 4-tier breakpoint) and a `ResizeObserver` on the container ref, so `size` is the *actual* container width (or `min(container, targetMax)`) rather than a hardcoded 520. This addresses D1 head-on.

### 7.3 Test strategy (usability, not geometry)

Every M1.4 Playwright test must assert, at every audited viewport:

1. `body.scrollWidth <= viewport.width + 1` (no horizontal disaster).
2. KG SVG's absolute `left + width` ≤ viewport.width and `left` ≥ 0 (not off-screen).
3. Every clickable node's *tap target* (hit-circle bbox) is ≥ 44 CSS-px diameter.
4. Zero pairwise label-bbox overlap.
5. Grid tracks in KG-containing grids never exceed viewport.width.
6. On mobile: exactly N nodes rendered where N ≤ 6 (selected + neighbors).
7. On tablet: exactly N nodes rendered where N ≤ 9 (center + ring 1 + selected branch).
8. On desktop: full topology (13 nodes) rendered without overlap.
9. Article panel never overflows its grid track.
10. Metadata table (or replacement) is either horizontally scrollable inside a bounded wrapper OR truly card-stacked (no internal 1451 px min-content).
